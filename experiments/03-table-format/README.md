# 03 表格格式：純文字、markdown、HTML、逐列鍵值，本機模型讀哪種最不會讀錯格

## 1. 想回答的問題

同一張法規表格，餵給本機模型時用 pdfplumber 文字層的攤平文字（01、02 的作法）、markdown 表、帶 colspan／rowspan 的 HTML、還是每列一行的鍵值對（KV），讀出正確數字的比率差多少？

## 2. 怎麼做

**語料**：02 用到的 17 張表（`data/01-chunking/attachments/*.pdf`，01 的 `fetch_corpus.py` 抓的）。`tables.py` 用 pdfplumber 的**格子幾何**算出每格真正的 colspan／rowspan（合併格是一個橫跨多條格線的 bbox），不是猜空格屬於左邊還是上面；兩件幾何看不出的事用規則：表頭深度 = 前四列中最後一個有 colspan 的列，再被表頭內的 rowspan 往下拉（表四○ 是轉置表，規則會錯，`build_corpus.py` 手動指定 1 列，這是唯一一張）；表二五～二／四／五 的資料列 PDF 沒畫線，一格塞 18 行，拆成一列一行（只在 ≥80% 的行是數字時拆，表九二 的文字格不拆）。表八六～三 對角線分割的角落格會產生一個全空的欄，整欄連表頭一起丟掉。四種格式由 `build_corpus.py` 產生，進 git（`corpus/`）；17 張我逐張對過 PDF 原圖，表九三～一 的標題只取第一行（第二行「接地之搭接導線線徑」掉了，四種格式都一樣）。

| 格式 | 做法 | 每張平均字元 | 角色 |
|---|---|---|---|
| flat | 01 的 `corpus/tables/*.txt`，文字層一列一行，欄位不對齊 | 336 | 盲測基線：現在的 pipeline |
| markdown | 多層表頭合成一列，欄名用「／」接（「三相220 V用戶／超過200」），`\| a \| b \|` | 568 | 最常見的 RAG 作法 |
| html | `<table>`，真的 colspan／rowspan，`<th>`／`<td>` | 1014 | Table Meets LLM 的贏家 |
| kv | 每個資料列一行：`欄名=值；欄名=值；…`，前面一行表名 | 1255 | Improving Agents 的贏家 |

每種都附表名與「註」。

**題庫** `questions.jsonl`：82 題，全部是表格題，答案是單一數值。22 題照抄 02（`src: "02:…"`，測試保證逐字相同），60 題新出，每張表 4–6 格、挑不同列不同欄，**正解對照 PDF 原圖標**（02 的表格正解是從攤平文字讀的，這次不信它）。正解格式同 02（`expect.value/unit/alt`，alt 是同義的值與單位）。Mike 抽查名單：n03、n17、n39、n44、n53。

**條件**：4 種格式 × 2 模型，加 closed-book（不給表）當雜訊底線，共 10 格 × 82 題 = 820 次呼叫，mini 上 51 分鐘。prompt、schema、模型設定**全部沿用 02**（schema 約束解碼；02 證明逼法無差），只換「依據」區塊的內容；qwen3:8b `think:false`、gpt-oss:20b `think:"low"`（關不掉，見 02），temperature 0、seed 0、num_ctx 8192。

**判定**：`score.py` 複製自 02（parse_ok／schema_ok／value_ok／value_only_ok，單位同義表），純程式不用 LLM 裁判。

**五條規矩怎麼套**：雜訊底線 = closed-book；盲測基線 = flat；信賴區間 = 重抽題目 2000 次的 bootstrap 95%，格式之間報配對差距；記版本 = 下表；漂移探針 = 跑完每格重打 2 題（20 次），**18/20 逐字相同**，不同的 2 次都是 gpt-oss 的 t01（markdown 與 html 各一次），seed 0 也擋不住它。

按表看（`results/scored.jsonl`）：
- **表九三～一** 四種格式兩個模型都慘（qwen3 0–.25、gpt-oss 0–.5）：列是範圍（「38 - 50」「超過 80 - 200」），題目給的數字落在範圍邊界，模型挑錯列，或被「註」裡的「12.5 %」「80 mm2」引走。
- **表二五～二／四／五**（7 欄 21 列的寬表）：qwen3 不管什麼格式都只有 .2–.8，常把「22 平方」看成「60」那列、把「7-9 條」看成「4」那欄；gpt-oss 用 markdown 全對。
- **表八六～三**（多層表頭）：qwen3 flat 6/6 全對，三種結構化格式各錯 1 題（t13a）；gpt-oss 最好的是 markdown 5/6。結構化不保證贏。
- HTML 對 qwen3 是負的：它常把 `<td>` 裡的數字當答案卻對錯欄，quote 只抄一個數字；gpt-oss 在 html 下出現「0.025 kA」這種自行換算。

## 4. 結論

**同一張表從攤平文字換成 markdown 或逐列鍵值，本機模型讀對格的比率 qwen3 .67 → .79／.84、gpt-oss .73 → .95／.87，差距的 95% 區間都不含 0；HTML 沒有幫助（qwen3 −.04、gpt-oss +.10，都分不出）。gpt-oss 用 markdown 最好、qwen3 用 kv 最好，兩者之間分不分得出看模型。**

次要的：閉卷 .05–.06，答對確實靠讀表；範圍列（「38 - 50」）和寬表（7 欄 21 列）是剩下錯誤的主因，格式換了也救不了；kv 字元數是 flat 的 3.7 倍，markdown 只有 1.7 倍，同樣的準度 markdown 比較省。

## 5. 沒做到的、下次想試的

- **範圍列要另外處理**：表九三～一、表二五～六 這種「38 - 50 → 14」的查表，模型連 markdown 都挑錯列。可試把範圍展開成「下限／上限」兩欄，或在 prompt 裡寫「先找題目數字落在哪個範圍」。
- **寬表切列**：表二五～二 21 列 7 欄，qwen3 讀不準。可試只餵問到的那一列（先用題目的「22 平方」檢索列再餵），這就是 01 的 table-row 切法接到 02 的輸出端。
- **HTML 為什麼沒用**：Table Meets LLM 的結論是 GPT 系列上 HTML 最好，這裡 8B／20B 本機模型沒有。可能是 rowspan／colspan 要模型自己算座標；下次試「HTML 但表頭展平、不用 span」分開這兩個因素。
- **漂移 18/20**：gpt-oss 在 seed 0、temperature 0 下仍有 2/20 次回覆不同，README 第 3 節的 gpt-oss 數字要當成 ±1 題的精度看。
- **表頭深度與表四○**：表頭規則一張表要手動指定；真實 pipeline 要嘛接受這種人工，要嘛再找一個不靠規則的方法（版面模型）。
- **只有一種 prompt**：沒試「先列出相關列再回答」的兩段式（Table Meets LLM 的 self-augmented prompting）。

對 securag 的意思：表格不要攤成文字餵，至少轉成 markdown（pdfplumber 的格子加向前填就夠），寬表另外切列。
