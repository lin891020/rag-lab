# 20-api-ceiling：強模型上限——「點錯格」只有小模型會犯嗎

## 1. 想回答的問題

最強的模型（Claude Opus 5.5）在 C1／C4／C5 用三種給法——整張表給它讀、用 19 的查表工具、直接給正解列——各答對多少？它也會點錯格嗎？

## 2. 怎麼做

**為什麼做**：16–19 一路指向「小模型輸在知道要表上哪幾格」。19 把讀格子交給程式後，查到時答對 .86／1.0，但總分沒升，錯搬到「選哪幾列」（C4 分段只查一段、C5「以下」讀反）。還沒回答的是：這是 8B／20B 太小，還是這種題本身難？

**別人怎麼解的**：
- **TABVERSE（arXiv 2606.09578，2026）**：跨格式表格評測裡，前沿模型的查表錯多半是「對的欄、錯的列」或漏掉一個篩選條件，多項答案常漏項——跟 19 的錯同型。
- **ReasonTabQA（arXiv 2601.07280）**：工業場景表格題，Claude Opus 4.5 66、GPT-5.2 59。
- **Attributed Table Graphs（arXiv 2601.08444）**：Claude Opus 4.7 在 WikiTQ 78.6、TabFact 91.2，精確篩選與比較仍是弱點。
- **TableBench（AAAI 2025）／Table-R1（arXiv 2505.12415）**：大小模型有差距，專門訓練能縮小。
- **搜了沒找到**：同一組題「小模型 vs 前沿模型」在「整張表／查表工具／正解列」三種給法下的受控比較；專講「以下／分段累進」範圍表錯誤率的研究。

**計畫**：`docs/superpowers/plans/2026-11-02-20-api-ceiling.md`（Mike 2026-11-02 核准）。

**格**（每格 96 題，Claude 兩個模型各跑兩次：`cards`／`cards-2` 等）：

| 格 | 依據 | 來源 |
|---|---|---|
| cards | 整張表（17／18 的 cards） | 19 存的 `evidence_text`（gpt-oss 那份；兩個小模型的逐字相同），17 的提示逐字 |
| oracle | 直接給正解列與條文節錄（16／17 的 oracle） | 同上 |
| fix | 19 的兩步查表（無例子的提示、括號寬鬆比對） | 19 的 `lookup.py`、`lookup_prompt(fix=True)` |

小模型不重跑：qwen3（cards、oracle、fix）與 gpt-oss（cards、oracle、fix、fix-2）的 19 列照抄進來（`reused_from: "19"`），用同一支 `score.py` 重評。

**模型**：`claude-opus-5-5`（主角）、`claude-haiku-5-5`（便宜，看中間那段；只描述）。Claude API，`effort: "medium"`、`max_tokens` 16,000、structured outputs 照 19 的兩個 schema（送出時每個 object 補 `additionalProperties: false`、拿掉 `maxItems`；超過 6 格由 `parse_lookups` 截，照記）。**跟小模型的設定不同**：API 不收 temperature，所以每格跑兩次量雜訊；Opus 5.5 的 thinking 關不掉（Haiku 一樣開著），小模型是 qwen3 think 關、gpt-oss think low。

**跑前改的**（19 的審查找到的三處，20 的複本先修，各加測試）：`evidence.hit_stats` 不算用不到的那段（c4-16；照抄的 19 fix 列也照新算法重算）；`posthoc.step1_class` 把「列對、欄名寫錯」算成選錯欄；測試的 import 移到檔頭。

**跑前審查**（另一個 agent，用假的 API client 把整串離線跑一遍）：擋下一個會白花錢的 bug——19 的 oracle 列（來自 16／17）沒有 `tables_hit` 欄位，取欄位寫在呼叫 API 之後，每次 oracle 呼叫都會付完錢再存成錯誤列（384 次），而且不算進預算。改成呼叫前先組好欄位、缺的不取，`KeyError` 不再當成呼叫失敗（程式錯就直接停）；被拒答或截斷的呼叫也把 token 算進花費。審查也確認 cards／oracle 的提示跟 17／18 當時送的逐字相同（192 列）。

**試跑**（3 題，兩模型、六格，2026-11-02 23:29）：36 次 0 失敗、全是 end_turn；Opus 0.34 美元，推估全部約 11 美元，Haiku 約 0.35 美元。抽到的 3 題剛好都是該棄答題，算進正式結果（同設定）。

**主檢定**（跑 20 之前宣告；答對嚴格，有答案的 78 題，按題與 cluster 兩種 bootstrap，照 19）：
1. opus cards − gpt-oss cards（強模型讀整張表比小模型好多少）
2. opus fix − opus cards（查表工具對強模型是幫還是害）

描述、不下判定：opus oracle 與差距；haiku 三格；按鏈；第一步掉在哪一關（`posthoc.step1_class`）跟 19 兩模型並排；每格兩次的同答與差距；選小一級；該棄答 18 題；token 與花費。

**預期**（跑前寫）：opus cards .85–.95、oracle ≥ .95；opus fix − cards −.05～+.05 分不出；opus 在 fix 的「選錯列」比 19 兩模型少一半以上，但 C4 分段漏段仍有幾題；haiku 介於 gpt-oss 與 opus 之間。

**正式跑**：2026-11-02 試跑後接著跑，2026-11-03 00:39 跑完，mini；Claude 新跑 1,152 題次（兩模型 × 六格 × 96 題）、1,536 次呼叫（fix 一題兩次），0 失敗、全是 end_turn；回應的 `model` 跟送出的 id 相同。花費 US$11.26（Opus 10.91、Haiku 0.35；程式用 `usage` 加總，Console 還沒對）。`anthropic` 套件版本、token 明細在 `results/read/meta.json`。

## 4. 結論

**「點錯格」是小模型的問題：Opus 用查表工具 75 題全對、正解格一格沒漏，連 19 兩個小模型錯最多的 C4 分段、C5「以下」都沒犯；整張表給它讀也 .99，比 gpt-oss 好 .19。**

## 5. 沒做到的、下次想試的

- **題庫**：5 題已標 `defect` 不計分（16–20 都重算）；`16-rule-lookup-compute/build_questions.py` 的範本改成 110/220 V、「導線安培容量」。醫院手術室「全額」算不算對沒改，審查另列旅館題沒排除舞廳／飯廳、插座題沒寫第 37 條算法，都是小問題、照舊。
- **設定跟小模型不同**：Opus／Haiku 的 thinking 關不掉（effort medium），小模型是 qwen3 think 關、gpt-oss think low；API 不收 temperature。所以「大 vs 小」混了「有沒有想」。要分開就得讓 gpt-oss think high 或 qwen3 think 開，再跑一次。
- **依據沿用 19**：cards／oracle 用的是 19 存的 `evidence_text`，不是重新檢索。
- **fix 看不到適用條件**：工具只回格子，條文的適用條件不在第二步裡；被拿掉的題裡 Opus 因此照表硬算。19 第 5 節的「工具回整段」接著在 21 做。
- Console 的花費還沒跟程式加總對（計畫寫 ±5%）。
- 30B 本地模型在中間哪裡，沒量。
