# 23-ocr-size：送 OCR 前先縮圖——glm-ocr 會不會比較常回表格

## 1. 想回答的問題

同一張乾淨的 300 dpi 頁圖，送 glm-ocr 前先縮小，「整張表回純文字」會不會消失？答對率會不會因此上升，又會不會因為字太小而開始讀錯？

## 2. 怎麼做

**為什麼做**：22 量了品質差的掃描，答對率沒掉。glm-ocr（提示尾加換行，下稱 glm2）掉分只有一種情況：整張表回成純文字。300 dpi 乾淨頁有 2 張這樣（表九二、表四○），200 dpi 一般掃描有 3 張，150 dpi 很差的掃描反而 0 張。所以猜：圖小一點，它才回表格。但 22 的 150 dpi 那級同時加了模糊和雜訊，分不開是哪一個造成的。23 只改大小，其他都不動。

**別人怎麼解的**：
- **PaddleOCR-VL（arXiv 2603.24326，CVPR 2026）**：主張高解析度對文件解析很重要，尤其是密集的字和表格。文獻預期縮圖會變差，跟 22 的觀察相反。
- **TALENT（arXiv 2510.07098）**：Qwen2.5-VL-3B 讀表，512 → 1024 準確率 69.5 → 71.5。解析度高一點，只好一點。
- **GLM-OCR（arXiv 2603.10910）／官方 repo**：設定檔的 `max_pixels` 是 71,372,800。300 dpi 一頁約 870 萬像素，在範圍內，官方沒說要縮圖。
- **搜了沒找到**：「圖太大反而不回表格」的報告；任何 OCR 模型「縮圖比例 × 輸出格式」的掃描；ollama 的 glm-ocr 會不會自己縮圖的文件。

**計畫**：跑前寫好，Mike 2026-11-03 核准。

**縮圖**（`shrink.py`）：06 的 300 dpi 頁圖（RGB，2481×3508），用 PIL LANCZOS 等比縮小，存 PNG（無損），sha256 記在 `results/size_manifest.json`。只改大小，色彩模式照原圖。計畫原本寫「灰階照 22」，改成照原圖，這樣唯一的差別就是大小。圖存在 `data/23-size/`，不進 git，重跑 `shrink.py` 會得到逐位元相同的圖。

| 路線 | 比例 | 約當 | 圖 |
|---|---|---|---|
| glm2-s100 | 1.0（06 的圖本身） | 300 dpi | 2481×3508 |
| glm2-s83 | 0.83 | 250 dpi | 2059×2912 |
| glm2-s67 | 0.67 | 200 dpi | 1662×2350 |
| glm2-s50 | 0.5 | 150 dpi | 1240×1754 |
| glm2-s33 | 0.33 | 100 dpi | 819×1158 |

**OCR**（`read_sizes.py`）：glm-ocr 走 host 的 ollama，提示與設定照 06／22。每頁記回的格式、`done_reason`、輸出 token，以及 `prompt_eval_count`（圖變成多少 token）。

**結構層**（`structure.py`，照 22）：格子、數字格、列的召回，對文字層。

**答題層**（`run.py`、`score.py`、`report.py`，照 22）：06 的 82 題、提示、schema、模型設定（qwen3 think 關、gpt-oss think low、temperature 0、seed 0）都照用。條件：clean（文字層，同一晚重跑當盲測基線）、glm2-s100／s83／s67／s50／s33，× qwen3、gpt-oss × 82 題 = 984 次，加上漂移探針。

**主檢定**（跑前宣告；答對要嚴格，82 題；按題與按表 cluster 兩種 bootstrap 的 95% 區間都不含 0，才算分得出）：glm2-s50 − glm2-s100，兩個模型各一個。

**預期**（寫在計畫裡，核准時就定了，比試跑早）：
- s50 回純文字 0 張，格子召回 ≥ .97。
- s33 格子召回開始掉（< .95）。
- 主檢定 +.02～+.05，分不出：只有表九二、表四○ 的 9 題會被救到。
- 如果各大小的圖片 token 數都一樣，以上預期作廢，改寫成「ollama 內部有縮圖」。

**描述、不下判定**：
- 每一級回純文字的表、圖片 token 數、格子召回。
- 表九二、表四○ 那 9 題的答對數。
- 組合做法「先用原圖讀，回純文字的表改用 s50」：從已經問過的列直接拼出來，不多呼叫模型。每題的依據只有它的正解表，所以組合下的提示跟 s50 或 s100 那份逐字相同（`posthoc23.py`）。

**試跑**（2026-11-03 21:04，表九二、表四○ 第 1 頁 × 5 級，寫到暫存資料夾；**看到結果之前預期已經寫好**）：
- 0 失敗，都是 `stop`。
- **圖片 token：s100、s83、s67 都是 4,044**，s50 是 2,788，s33 是 1,205。也就是說，ollama 會先把大圖縮到一個上限，再交給 glm-ocr。前三級的模型輸入幾乎一樣（輸出 token 也逐頁相同），真正不同的只有 s50 和 s33。這不是「每一級都一樣」，所以預期不作廢，但 s83、s67 只能當「上限確認」看。
- 表九二 在 s50 回成 HTML 表，其他級都是純文字；表四○ 五級都是純文字。（22 在 150 dpi 重新轉圖，加模糊、雜訊之後，表四○ 是回表格的。）
- 答題層沒試跑：`run.py` 跟 22 一樣，只是改從 `read_sizes` 檢查 corpus 齊全。
