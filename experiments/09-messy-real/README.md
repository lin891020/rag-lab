# 09 天生就亂的真資料：30 份公報法規修正案，08 的對照表準不準

## 1. 想回答的問題

08 用人工弄亂的法規做了一張「亂 → 壞在哪一步 → 掉幾分 → 修法」的對照表。拿 30 份天生就亂的政府公報法規修正公告（預告草案的三欄對照表、令修正的條文全文、地方公報、掃描頁、亂碼頁、橫式附表），01–08 的 pipeline 不改直接上：160 題找得到幾成、答得對幾成？掉的題是 08 預測到的哪一列，還是沒預測到的新亂？08 建議的修法各救回幾分？

## 2. 怎麼做

**別人怎麼解的**：
- **對照表的格式是法定的**：行政院「中央行政機關法制作業應注意事項」規定修正案用三欄（修正條文／現行條文／說明），88 年函定劃線原則。欄位固定，所以可以按欄解析。**沒找到**解析對照表的開源程式。
- **跨頁表格**：05 的接續規則（前表到頁底、後表在頁頂、欄界對齊）本來要直接拿來接對照表，實測 0/4 對接上——每頁表格底下有頁碼，05 的「表下沒字」檢查把頁碼當成表的結尾。08 說頁首頁尾無害，是對檢索無害；對 05 的規則有害。改用「列首有沒有條號」判斷續列（`extract.compare_rows`）。
- **表格列當 chunk**：STC（arXiv 2605.00318）每列一個 key-value 塊、FT-RAG 拆到格子並保留表頭路徑，都報優於整表一塊 → 對照表一條一塊，塊裡帶「修正條文／現行條文／說明」三個欄名。
- **多份相似文件撈錯份**：Multi-Meta-RAG（arXiv 2406.13213）從問題抽來源過濾再檢索；HiQA（arXiv 2402.01767）每塊掛階層 metadata → 便宜版 = 07 的標題鏈前綴（每塊加《法規名》），當一個條件。
- **修正前後**：LeKUBE（arXiv 2407.14192）出「修法後答案會變」的題 → 題目一律問「修正後」或「這次修正」，避開 08 第 5 節說量不到的「兩版並存」。
- **cid 亂碼**：嵌入字型沒有 ToUnicode 表時 pdfminer／pypdf／PyMuPDF 都只能吐 `(cid:N)` 或私用區碼（三個都試過），社群解法只有 OCR。
- **本機**：01 `chunkers`／`retrievers`／`metrics`、06 `ocr.glm_ocr`、08 `doc_health`、08 `labels` 的「整行見證」作法改成「題目帶原文 quote、去空白比對」。

**語料**（`build_corpus.py`，`corpus/manifest.json`）：國家圖書館政府公報開放資料 `gov.xml`（2024-07～12 半年快照，11,403 筆、10,438 筆有 PDF）→ 案由含「修正」且含條文／規則／辦法／標準、有檔、3–30 頁 → 694 筆 → 分層抽 30（seed 0，掃了 233 筆才湊齊）：

| 層 | 數 | 說明 |
|---|---|---|
| 預告草案（draft） | 15 | 三欄對照表（修正條文／現行條文／說明），或附表的「修正規定／現行規定」 |
| 令修正（final） | 15 | 修正後的條文全文；總統府公報的一筆會夾著前後幾部法律 |
| 地方公報 | 14 | 嘉義、南投、苗栗、臺中、臺東、宜蘭、屏東、彰化… |
| PDF 產生器 | iText 12、iLovePDF 6、Word 6、Distiller 2、其他 4 | |
| 有掃描頁（沒文字層） | 4 份 | E2422448 2/6 頁、E2426379 9/10、E2428802 2/3、E2430372 2/3 |
| 文字層是 `(cid:N)` 亂碼 | 1 份 | E2423739：29 頁有 28 頁，share .955 |
| 有橫式（旋轉）附表頁 | 7 份 | pdfplumber 把字倒著讀（「說明」變「明說」），pypdf／PyMuPDF 正常 |

共 243 頁、中位數 5 頁；PDF 進 git（17 MB）。體檢（`doc_health.py`，08 的加兩欄：`garbage_pages`、`rotated_pages`）結果在 `corpus/health.csv`：30 份裡 23 份有頁首頁尾重複行、17 份 lines 策略找得到表、0 份被標成對齊文字或兩欄。

**抽字三路線**（`extract.py`，`corpus/text/<sysid>.<route>.txt`）：

| 路線 | 做什麼 | 對應 08 的修法 |
|---|---|---|
| base | 01 的 pypdf 抽字，一字不改 | 盲測基線 |
| ocr | 體檢標出的頁（沒字、或 cid 占比 ≥ .2）換成 glm-ocr「Text Recognition:」讀圖的文字（10 秒/頁），其餘頁同 base | 掃描頁 → OCR |
| rows | 預告草案的對照表用 pdfplumber 格子重建成「一條一筆」（條號｜修正條文｜現行條文｜說明），跨頁的格子接回、說明欄被畫成子欄的摺回；旋轉頁跳過；其餘頁同 base。令修正同 base | 跨頁表 → 接回 |

**切塊四種**：`article`（01 的 `parse_articles`，`^第 N 條$` 獨立成行——公報寫「第十四條之一　漁船…」，預期一條都找不到）、`article-cn`（中文數字條號、同行有內文，最小修改）、`article-cn+pre`（同上，但公告與總說明那些「條文之前的字」留成固定塊，不丟）、`fixed-1000`（01 的保底）。每種再 × 有無《法規名》前綴。

**檢索軌**（`run_retrieval.py`）：30 份一起建索引；dense bge-m3 ／ bm25 字二元組 ／ random；3 路線 × 4 切塊 × 2 前綴 × 3 檢索器 = 72 格 × 160 題。命中 = 排進來的塊來自該題的文件、且去空白後含該題的 `quote`；hit@5 看前五塊、hit@1000 照 01 的預算走（整塊放得下才算）。

**錯因歸類**（`attribute.py`）：每個沒命中的（格, 題）依序判定：`no_chunks`（這份一塊都沒切出來＝08 的切塊前提壞）、`garbage`／`no_text`／`rotated`／`extract_other`（quote 不在這路線的文字裡，看體檢欄位分）、`preamble_dropped`（quote 在條文之前、切條把它丟了）、`chunk_cut`（在文字裡但沒有一塊整個含住＝08 的塊界）、`wrong_doc`（前五塊沒有這份＝08 的撈錯份）、`ranked_low`。

**閱讀軌**（`run_read.py`、`score.py`）：qwen3:8b `think:false`、gpt-oss:20b `think:"low"`、temperature 0、seed 0、JSON schema。五個條件：closed-book（雜訊底線）、oracle（直接給 quote 前後 1,000 字＝閱讀上限，把檢索損失跟閱讀損失分開）、base（base／article／無前綴的 dense 排名，整塊塞滿 1,000 字）、fixed（base／fixed-1000）、all（rows／article-cn+pre／前綴）。三種題型全部客觀評分：數字題照 06 的 value+unit；條號題集合完全相等（「第十二條之一」「12-1」「12之1」摺成同一個）；哪一份題法規名去括號後相等或包含。

**題庫**（`questions.jsonl`）：160 題（數字 109、條號 18、哪一份 33），我出、我核。每份 4–6 題：數字題（金額、天數、人數，問「修正後」的數字，現行欄是誘餌）、條號題（這次修正哪幾條）、哪一份題（哪個法規規定了 X）。每題帶 `quote`（原文一句，去空白比對），`tests/test_questions.py` 驗證每題的 quote 都在該份的 base 或 ocr 文字裡。抽查名單給 Mike 的 15 題見第 5 節。

**五條規矩**：雜訊底線 random／closed-book；盲測基線 base（01–08 的 pipeline 一字不改）；bootstrap 95% + 每個修法對 base 的配對差距；版本表（下）；漂移探針 = 向量 cache 對新算的 cosine、答題每格重打 2 題。

看錯在哪：
- **01 的切條在公報上一條都切不出來**（160/160 `no_chunks`）：公報寫「第十四條之一　漁船…」中文數字、跟內文同一行，01 的規則要「第 14 條」獨立成行。08 對照表那列「切塊前提壞」中了，但壞法不是 08 模擬的「條號被黏掉」，是**條號格式本來就不一樣**。
- **改了條號規則還是有 10 份切不出**（52 題 `no_chunks`）：要點用「四、九、十一、」不用條，附表類公告根本沒有條文，總統府公報的法律用「第 八 條」（有切到）。這 10 份只能靠 fixed-1000 或 +pre。
- **前言被切條丟掉**（13 題）：「這次修正哪幾條」的答案在公告主旨與總說明，條文裡沒有。08 沒預測到。
- **掃描頁 14 題、亂碼頁 6 題**：體檢抓得到，OCR 一路救回（+.11）；亂碼那份（E2423739，29 頁有 28 頁是 `(cid:N)`）08 的體檢會說「有文字層」。
- **預算**（34–52 題 `over_budget`）：gold 塊在前五名，但 1,000 字的塊加一行標頭或《法規名》就放不進 1,000 的預算。08 說頁首頁尾多 13 字無害，是因為那時的塊都遠小於預算；這裡塊剛好切到預算大小，多 20 字就整塊出局。這是量法跟切塊大小的耦合，不是檢索壞；hit@2000 消掉它之後前綴對 hit@2000 沒差、對 hit@5 +.04。
- **對照表一條一筆沒差**：rows 路線在 15 份草案裡只有 7 份找得到三欄表（其餘是附表、掃描、旋轉頁），而 base 的 pypdf 本來就把三欄的格子照串流順序讀成「修正條文一整格、現行條文一整格」，一條一塊切條時兩欄各自成塊，quote 都找得到。對檢索命中沒差，對閱讀（答案要從修正欄而不是現行欄抄）才有差，看閱讀軌。
- **真的撈錯**：最好的格只剩 9 題 `ranked_low`，其中 3 題在 E2428764（嘉義市特教推行委員會：那一筆公報頁面同時夾著另一部辦法的尾巴）、2 題在 E2421820（旋轉的收費表，base 文字是打散的格子）。

### 閱讀軌：160 題 × 5 條件 × 2 模型（`results/read/summary.csv`）

1,620 次答題 141 分鐘、0 次錯誤、JSON 全部合格（parse／schema 1.00，qwen3 base 差 1 題）；漂移探針 19/20 同（差的是 gpt-oss／all／q001）。value_ok 是嚴格評分（數字對、單位也要對）；括號內是「數字對、單位算錯」也算對的寬鬆分，差距全來自單位（下面說）。

把檢索損失跟閱讀損失拆開：依據**含**正解時 all 答對 .88／.78（qwen3／gpt-oss），fixed .74／.66；**不含**時 .18–.27（鄰塊猜到或閉卷知道）。all 的 45 題不含正解裡 20 題來自掃描／亂碼那 5 份——rows 路線沒接 OCR（抽字是 base 的頁加對照表重建），所以 all 條件**沒含** OCR 這個修法；扣掉那 5 份，all 是 .77／.69。檢索軌說 OCR 值 +.11，閱讀軌沒量到。

看錯在哪：
- **不改的 pipeline 等於閉卷**（base − closed-book 區間含 0）：一份一塊、沒有一塊放得進 1,000 字，依據永遠是整份的前 1,000 字。
- **哪一份題 fixed .21–.24 → all .85**：法規名在公告主旨（前言塊）與《法規名》前綴裡，fixed-1000 的塊只有條文內容；檢索軌量不到這一項（命中只看 quote），閱讀軌才看得到前綴值多少。
- **修正欄 vs 現行欄**：fixed 給的是 pypdf 串流順序的格子，兩個模型都抄現行欄（q006 汞 0.4 vs 修正後 0.3）；all 的 rows 路線在格子前標「修正條文：／現行條文：」，同一題兩個模型都對。這是 rows 路線在閱讀軌的價值，檢索軌（±.02）看不到。
- **oracle 掉的 .16–.18**（42 題至少一個模型錯、13 題兩個都錯）：① 單位——gpt-oss 問「第幾條」「幾人」「幾年」「幾次」時把 unit 填空字串（15 題）、qwen3 把「個月」寫成「月」（5）、「工作日」寫成「日」（2），06 的別名表沒這些；② 1,000 字的窗只含一條，條號題的答案要整份（q050／q061／q067 兩個模型都只列窗裡那一條），所以條號題的 oracle .61／.83 是上限的下限；③ 中文數字「三萬六百」兩個模型都讀成 36,000（q143）；④ 附表攤成文字後數字對不回列（q021／q022／q026）；⑤ 同一窗裡兩部法規挑錯（q128）。


## 4. 結論

**真資料上 08 的對照表「症狀」中了三列（切塊前提壞、掃描頁、撈錯份）但「原因」沒有一列跟模擬的一樣；沒預測到的四種新亂（cid 亂碼、前言被切條丟掉、要點與附表沒有條、1,000 字塊撞 1,000 字預算）佔了剩下的失分；不改的 pipeline 檢索 .00、閱讀等於閉卷，三個修法（中文條號 +.55、前言留塊 +.23、OCR +.11）把檢索拉到 .89 [.83, .93]，閱讀 .71／.64，上限 .84／.82。**

## 5. 沒做到的、下次想試的

- **Mike 抽查 15 題**（seed 9）：q001、q014、q037、q057、q065、q067、q091、q097、q125、q126、q138、q144、q148、q153、q157。每題看 `questions.jsonl` 的 question／quote／expect 跟 `corpus/pdf/<doc>.pdf` 對不對。
- **all 條件沒含 OCR**：rows 路線只接對照表重建，沒把 ocr 的頁接進來，掃描／亂碼那 20 題在閱讀軌永遠沒正解。下次 rows 要疊在 ocr 上，或加一個 `ocr+rows` 條件。
- **三個修法在閱讀軌綁在一起**：all = rows + article-cn+pre + 前綴，各自對閱讀的貢獻只從題型旁證（前綴→哪一份題、rows→修正欄），沒單獨量。
