# 26-hosted-retrieval：雲端模型做規則查表計算——檢索還是瓶頸嗎

## 1. 想回答的問題

16 的「查規則再計算」160 題，改用雲端模型（Claude Haiku 5.5、Opus 5.5）答，依據分別是閉卷、17 的三種檢索結果、正解列，各答對多少？檢索是不是仍然是最大的損失？

## 2. 怎麼做

**為什麼做**：25 給正解那張表時，雲端模型怎麼給都到頂。實際系統要的是：
- 自己從整部規則撈出對的條文與表格列。
- 再算數字或選線徑。

16／17 用本機小模型量的結論是「檢索是瓶頸」：給正解列答對 .87／.69，靠檢索只有 .22–.58（127 題的基準）。20 只用 Opus 跑過其中三條鏈、兩種依據。

**別人怎麼解的**：
- **16／17**：本機小模型。最好的檢索法 decomp@4000，正解列全進依據 .78。
- **20**：Opus 在 C1／C4／C5（75 題）用 cards .99、oracle .99；C2（查＋修正）、C3（馬達三步）與閉卷沒跑過。
- **加拿大建築法規 RAG**（arXiv 2505.04666）：retriever 是最該優化的部分；沒有正解依據對檢索依據的比較。
- **Repository-level code QA**（PROMISE 2026，arXiv 2603.26567）：最好的 RAG 設定約 64%，檢索品質限制表現。
- **搜了沒找到**：同一組法規題，前沿雲端模型「閉卷／檢索／正解依據」的受控比較。

**計畫**：跑前寫好，Mike 2026-11-04 核准。

**題庫**：16 的 160 題、五條鏈（C1 單查、C2 查＋修正、C3 馬達分路、C4 幹線需量、C5 設備接地），與 17、20 逐位元相同。2026-11-03 標的 5 題 defect 不計分，所以計分 155 題：
- 有答案的 127 題。
- 該棄答的 28 題。

計畫寫的「125 題」是我算錯，離線測試抓到；defect 裡有 2 題本來就是棄答題。defect 題照樣有問（保持 17 的網格，約 US$0.45），只是不計分。右欄「正解列全進」是 17 在 127 題上的比率。

**五個條件**（17 的提示逐字；依據是 17 存下的 gpt-oss 那份，兩個小模型拿到的逐字相同）：

| 條件 | 依據 | 17 的正解列全進 |
|---|---|---|
| closed | 不給（17 提示裡的閉卷句） | — |
| struct@1500 | 一條一塊＋一列一塊，1,500 字（= 16 的 L1-struct） | .39 |
| cards | 17 選定的找法：每張表一張卡片，跟條文一起排，約 3,000 字 | .59 |
| decomp@4000 | 拆成子問題逐一檢索，約 4,000 字（17 最好的） | .77 |
| oracle | 正解條文節錄＋正解列 | 1.0 |

測試鎖住：640 個有依據的提示，長度都等於 17 當時送的。

**模型**：
- Haiku 5.5 每格兩次（第二次當雜訊底線）；Opus 5.5 每格一次。Opus 的雜訊底線用 20：cards、oracle 在 C1／C4／C5 是同一份提示。
- effort medium、structured outputs、schema（found、quote、expression、value、unit）照 20。
- 次數：Haiku 1,600、Opus 800。先 Haiku，再 Opus。
- 每次呼叫記帳，失敗、被停的也算；累計超過 US$25 就停，停下來問 Mike。
- 被停（拒答、max_tokens）或回覆解析不了，算答錯，該棄答的題也一樣；被停不重問，網路或伺服器錯誤才重問。
- score 碰到失敗列、過期列（提示 sha256 不同）或缺格就拒絕算分。

**尺**（16 的，照 20 的 `score.py`）：
- 數字題：相對誤差 ≤ 1%。
- 選型題：在表的梯上，等於是對；大一級可接受；大兩級以上錯；**小一級是 critical**。
- 棄答題：`found:false` 才對。
- 單位嚴格。

本機小模型（17 存下的 qwen3、gpt-oss 回覆）用同一把尺重算，放在旁邊比較，不重跑。

**花費估計**：約 US$14，約 1.5 小時。

**主檢定**（跑前宣告；答對嚴格，有答案的 127 題；按題與按 cluster 兩種 bootstrap 的 95% 區間都不含 0，才算分得出）。每個模型各兩個：
1. oracle − cards：檢索還是不是損失。
2. cards − struct@1500：好一點的檢索有沒有幫。

**描述、不下判定**：
- closed；decomp@4000。
- 按鏈。
- 正解列全進／不全時的答對。
- 該棄答的題；選小一級。
- Haiku 兩次同答、Opus 對 20 同答。
- 花費。

**預期**（寫在計畫裡，核准時就定了）：
- **Opus**：
  - closed .05–.20、struct@1500 .35–.50、cards .60–.75、decomp@4000 .70–.85、oracle ≥ .95。
  - oracle − cards +.20～+.35，分得出。
  - cards − struct@1500 +.15～+.30，分得出。
- **Haiku**：
  - 各格比 Opus 低 0–.10；oracle .85–.95。
  - 兩個主檢定也分得出。
- **正解列全進時**：Opus ≥ .95；不全時 ≤ .20。也就是說，雲端模型的答對率幾乎等於「檢索有沒有撈到」。
- **雜訊**：Haiku 兩次同答 ≥ 145/155；Opus 對 20 同答 ≥ 88/91。

**跑前審查**（另一個 agent，用假的 API client 離線跑過，沒打 API）：沒有會讓數字錯或白花錢的問題。確認了：
- 640 個提示跟 17 送的一樣長，閉卷提示跟 16 的 L0 一樣長。
- 17 兩次 struct@1500 的依據逐字相同。
- 本機列用這把尺重算，跟 17 自己的分數 0 列不同。
- 20 的 192 列 cards／oracle 提示跟 26 相同。
- 估計 Opus 約 US$13。

照建議改的小地方：
- 一個模型整個沒有列也算缺格。
- 回覆空白或解析不了算錯。
- 報告只對主檢定下判定。
- 拿掉不適用的 `expr_ok`。
- 右欄比率改成 127 題的基準。

**試跑**（2026-11-04 12:10，寫到暫存資料夾，不算進結果；**預期在試跑之前就寫好了**）：
- 每鏈 1 題（c1-07～c5-07，都是有答案的題）× 5 條件 × 2 模型 = 50 次。
- 0 失敗，US$0.45，192 秒。
- 輸入 token：closed 約 1,000；struct@1500 約 2,500；cards 約 3,500–4,200；decomp@4000 約 4,400–5,300；oracle 約 1,100–2,300。
- 照這個推估全部約 US$15、約 2.5 小時。
- 先看到的：依據裡沒有正解列時，兩個模型多半回 `found:false`（棄答），不硬答。
