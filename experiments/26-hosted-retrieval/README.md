# 26-hosted-retrieval：雲端模型做規則查表計算——檢索還是瓶頸嗎

## 1. 想回答的問題

16 的「查規則再計算」160 題，改用雲端模型（Claude Haiku 5.5、Opus 5.5）答，依據分別是閉卷、17 的三種檢索結果、正解列，各答對多少？檢索是不是仍然是最大的損失？

## 2. 怎麼做

**為什麼做**：25 給正解那張表時，雲端模型怎麼給都到頂。實際系統要的是：
- 自己從整部規則撈出對的條文與表格列。
- 再算數字或選線徑。

16／17 用本機小模型量的結論是「檢索是瓶頸」：給正解列答對 .87／.69，靠檢索只有 .22–.58（127 題的基準）。20 只用 Opus 跑過其中三條鏈、兩種依據。

**別人怎麼解的**：
- **16／17**：本機小模型。最好的檢索法 decomp@4000，正解列全進依據 .78。
- **20**：Opus 在 C1／C4／C5（75 題）用 cards .99、oracle .99；C2（查＋修正）、C3（馬達三步）與閉卷沒跑過。
- **加拿大建築法規 RAG**（arXiv 2505.04666）：retriever 是最該優化的部分；沒有正解依據對檢索依據的比較。
- **Repository-level code QA**（PROMISE 2026，arXiv 2603.26567）：最好的 RAG 設定約 64%，檢索品質限制表現。
- **搜了沒找到**：同一組法規題，前沿雲端模型「閉卷／檢索／正解依據」的受控比較。

**計畫**：跑前寫好，Mike 2026-11-04 核准。

**oracle 不是 1.0，原因是 oracle 給得太少，不是讀錯**：
- Opus 的 9 題錯全是 C3 馬達題的棄答。oracle 只給表二五～五 正解那一列（例：14 mm² 50 A）；題目問「最小幾平方」，依據裡沒有小一級那列，證明不了它不夠，模型照規則回找不到。
- Haiku 另外 C4 有 3 題棄答：oracle 只給表五二「場所=其他」那列，題目寫「辦公大樓」，它不敢認定辦公大樓算「其他」。cards 給整張表，Haiku C4 是 1.0。

**閉卷**：
- Haiku 計分的 155 題、兩次都回 `found:false`。閉卷提示有兩句互相打架：規則說「不要用你自己知道的數值補」，依據行說「請依你的知識回答」。Haiku 照前一句，Opus 照後一句。
- Opus 答了 74 題，對 51、錯 23（其中 5 題選小一級）；該棄答的 28 題硬答 4 題。對的集中在 C5 接地表二六～二（.85）與 C4 需量因數表（.83），引句多自己註明「憑記憶」。所以 Opus 閉卷 .40 跟 struct@1500 .39 一樣（−.01 [−.08, +.06]），但閉卷錯的會錯得很有自信。

**該棄答的 28 題**：有依據時 Haiku 全部棄答（1.0），Opus .96–1.0；17 的 qwen3 cards .00、gpt-oss cards .46。

## 4. 結論

換成雲端模型，檢索仍是最大的損失（oracle − cards Opus +.32、Haiku +.24，分得出），而且答對率幾乎就等於「檢索有沒有把正解列撈全」：撈全時 Opus 221/223 對、沒撈全時 3/158，有依據時它答出口的 342 次全對，錯的都變成「找不到」。

## 5. 沒做到的、下次想試的

- **oracle 要給整欄或整張表，不要只給正解那一列。** 選型題得證明小一級不夠，小心的模型才敢答；這次 oracle 反而低估了上限（Opus C3 9 題棄答）。真正的上限比較接近「檢索撈全」那組的 221/223。
- **閉卷提示要改成不打架**，不然閉卷數字量的是「模型聽哪一句」，不是「模型記得多少」。也要記住 Opus 記得這部規則的部分附表：之後若讓它在沒撈到時照記憶答，會出現「對的不少、錯的很自信」（74 題錯 23、選小 5）。沒撈到就擋在程式層（呼應 11）。
- **下一步該花在檢索召回，不是閱讀。** decomp@4000 還有 29 題正解列沒撈全；可以試讓雲端模型自己發查詢、多輪檢索或叫查表工具（20、21 的工具改成回整欄），看撈全率能不能從 .77 往上推。
- **Haiku 在檢索依據上跟 Opus 同分**（cards +.00），便宜 36 倍；但有依據時 Haiku 會選小一級（5 次），Opus 0 次。要上線得擋：程式驗算「選出的線徑載流量 ≥ 需求電流」。
- 沒跑 Sonnet 5.5；沒有比 16 這批更難、跨三張表以上的題；也還沒拿真的圖面或規格書出題。
