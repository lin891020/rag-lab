# 17 怎麼把對的表格列找回來：16 的檢索瓶頸，換「先找表、整張給」與「分步查」各救回多少

## 1. 想回答的問題

16 的查表接計算題，答對幾乎全看正解列有沒有進依據（全進只有 .41）；把找法從「一列一塊、dense 前幾名」換成「先找表、整張給」或「先把題目拆成要查哪幾樣、分別找」，正解列全進依據的比例與答對率各回到多少、離 oracle 還差多少？

## 2. 怎麼做

**別人怎麼解的**：
- **TableRAG（Google, NeurIPS 2024）**：大表先做 schema 檢索（欄名＋範例值）再做 cell 檢索。→ 這裡的「表卡片」是 schema 那一層；我們的表小（≤1,500 字），找到表就整張給，不再做 cell 檢索。
- **多跳拆題**：TableRAG（arXiv 2506.10380，異質文件）、ST-Raptor（2508.18190）、TabDSR（2511.02219）先把題目拆成子查詢再逐步查；TTQA-RS（2406.14732）說模型一步做多層推理會掉分。→ 「分步查」那一格只做「拆成要查哪幾樣」，不做邊算邊查。
- **列 vs 整張表**：Towards Data Science〈Retrieve one row, not the whole table〉——查單一值用列，同一張表命中很多列就改給整張；LangChain〈Benchmarking RAG on tables〉——表格塊會被本文塊擠掉。兩者都沒有受控的頭對頭比較。
- **本機**：12（bge-reranker-v2-m3 在前 50 裡重排，hit@1 .76 → .93，前提是正解在前 50）；04（整張乾淨表餵進去 .79／.91）；07（dense＋BM25 RRF 在條文上沒幫助）；16 的全套程式、題庫、乾淨表、尺。
- **搜了沒找到**：針對「法規附表、要兩張表接力查」的檢索比較。

**計畫**：`docs/superpowers/plans/2026-10-31-17-table-retrieval.md`（Mike 2026-10-31 核准）。

**開工前先量的**（16 的嵌入快取，沒打模型）：C1–C3 的正解列在 dense 前 50 名裡只有 .13–.27，前 5 名 .00–.06——**在前 50 上重排救不了**。前幾名被 87 張原始表的逐列塊佔滿（每塊重複一大段表頭）；C3 要的導線列取決於算出來的電流，題目裡沒有那個數。

**開工後發現、計畫外加的**（都在閱讀軌開跑前、只看檢索數字時決定，README 照實記）：
1. **16 的乾淨表丟了副標**。PDF 每張表標題下一行的「（導線絕緣物最高容許溫度 60℃，周圍溫度 35℃）」清表時沒收，於是表二五～二／三／四 三張表標題一字不差（「金屬導線管配線之導線安培容量」），只差在 60／75／90℃——**檢索與模型都分不出哪張是幾度的表**。17 從 01 的附表文字補回 5 張表的副標（二五～二、三、四、五、二五八～三），所有新格都用補回的；加 `struct@3000-nosub` 當對照，主檢定多一個「補副標本身」。16 的數字是在缺副標的表上量的（第 5 節）。
2. **cards+rr 沒過門檻**：比 cards 只高 +.01（門檻 +.05），不進閱讀軌，只報檢索數字。
3. **@4000 三格**：C3 的兩張表（電動機表 1,454 字＋PVC 管表 1,019 字）在 3,000 字裡塞不進第一名旁邊，於是加 struct／cards／decomp @4000 看預算的上限效果；`decomp@4000` 進閱讀軌，**只描述、不下判定**。

**qwen3 讀整張表會讀錯欄**：同一題「75℃、2.0 mm 單線、管內 8 條」，一列一塊（每個值前面寫著欄名「…／7-9／安培容量=16」）答 16；整張表（markdown，欄名只在表頭一次）找到 2.0 那列卻取第一欄「3 以下」的 23。gpt-oss 兩種都答對。歸因裡 qwen3 的「算式選錯」從 struct@3000 的 5 升到 cards 22、decomp 27，「抄錯值」從 22 升到 decomp@4000 的 42；撈錯列則從 77（struct@1500）降到 27（decomp@4000）——**撈對了，讀錯了**。gpt-oss 的撈錯列 77 → 23，抄錯值與算式選錯只多幾題。

**該棄答題**（30 題，gold 是表上的空白格）：qwen3 有棄答 struct@3000 6／cards、decomp、decomp@4000 都是 0；gpt-oss 23 → 14／13／15。整張表給時空白格旁邊就有數字，模型拿來答；一列一塊時空白那列常常根本沒撈到，「答對棄答」是因為沒找到——**這個指標跨格不能比**。

**漂移探針與重跑**：qwen3 沿用兩格各 10/10 一字不差；gpt-oss oracle 答案 10/10 相同（原文 8/10），struct@1500 答案只有 7/10 相同 → 照計畫（≥ 18/20）整格重跑（`run_read.py --redo`）。重跑 160 題跟 16 的同一格比：原始輸出一字不差 90/160、答案相同 127/160、130 題裡 9 題對錯翻面、答對 −.04 [−.08, +.00]——**同一模型、同一提示、temperature 0、seed 0，gpt-oss 重跑一次答對率就能晃 .04**。表裡的 struct@1500 用重跑的；用 16 的那份時檢定 3 是 +.02 [−.03, +.06] 分不出，所以 gpt-oss 的檢定 3 不採信。新格探針 20/20 一字不差。16 的雜訊底線（L0 .01／.00）低估了 gpt-oss 的重跑雜訊。

**跟事先宣告的預期比**：正解列全進 struct@3000 .55（預期 ≈ .5，中）、cards .60（≈ .75，沒中）、decomp .67（≈ .85，沒中）；cards − struct@3000 ≥ +.15（gpt-oss +.11、qwen3 −.03，沒中）；decomp − cards +.05～+.10（−.02／−.05，沒中）；預算本身 +.05 以內（中）；最好的格比 oracle 低 .10 以上（中，低 .29／.41）。補副標是計畫外加的，沒有預期。

**時間**：一次呼叫 qwen3 struct@1500 11.7 秒 → @3000 19–21 秒（提示長 1.6 倍，回答長度幾乎不變：token 中位數 100 → 128），gpt-oss 12–15 秒。

## 4. 結論

查表題最大的一步不是換找法，是**把清表時丟掉的副標補回來**（60／75／90℃ 三張同名表分得開，兩模型答對都 +.15）；「先找表、整張給」只對 gpt-oss 有用（+.11），qwen3 拿到整張表會讀錯欄、把撈對的好處抵掉；拆題讓正解列全進從 .60 升到 .67，答對卻沒升；最好的格離 oracle 仍差 .29／.41。

## 5. 沒做到的、下次想試的

- **整張表、但每格帶欄名**：把 cards 的整張表改成 kv（一列一行、每個值前面寫欄名），看 qwen3 的讀錯欄會不會消失。這是 17 最直接的下一步。
- **邊算邊查沒做**：decomp 只拆「要查哪幾樣」，C3 的第二張表取決於算出來的電流，留給「規則寫成程式」那一步（11/2 後）。
- 卡片格式（表號＋表名＋副標＋欄名＋列鍵）是看過這份題庫的失敗才定的；子查詢只用 qwen3 寫，兩個閱讀模型共用；decomp@4000 是看過檢索數字才加的，只描述。
- **gpt-oss 不是逐字重現的**：同設定重跑答對晃 .04；以後 gpt-oss 的差距要比這大才算，或者每格跑兩次取平均。雜訊底線應該用「同格重跑」量，不是 L0。
- 該棄答題的指標跨格不能比（見第 3 節）；要比得換成「依據裡有那個空白格時有沒有棄答」。
- 16 的數字是在缺副標的乾淨表上量的（16 README 已加註）。
- 審查時記下的：【段 i】分隔讓 struct 超出預算約 2–5%；報表裡「答對（寬鬆）」與「選小」也列在主檢定表，判定只看「答對（嚴格）」；歸因順序跟 16 不同（先看正解列在不在）；`decompose.py` 沒記 qwen3 digest（同一天、閱讀軌開跑時檢查過相同）。
