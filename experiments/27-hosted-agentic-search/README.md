# 27-hosted-agentic-search：雲端模型自己查——讓模型下查詢、查不夠再查，能把「撈全」推多高

## 1. 想回答的問題

16 的「查規則再計算」160 題，給 Claude Haiku 5.5／Opus 5.5 一支 `search` 工具（跟 26 的 cards 同一個索引、同一種打包），讓模型自己決定查什麼、查幾次（最多 5 次），撈全率和答對率比 26 的 cards、decomp@4000 各高多少？

## 2. 怎麼做

**為什麼做**：26 的結論是答對率幾乎等於「檢索有沒有把正解列撈全」：
- 撈全時 Opus 221/223 對，沒撈全 3/158。
- 有依據時答出口的 342 次全對，錯的都是「找不到」。
- 最好的固定流程 decomp@4000（qwen3 先拆子查詢、各自檢索）也只撈全 .77。

閱讀已經不是問題，剩下的是檢索召回。用雲端 API 時最直接的做法，是讓模型自己查。

**別人怎麼解的**：
- **IRCoT**（Trivedi 等，ACL 2023，arXiv 2212.10509）：檢索跟推理交替，用推理到一半的內容當下一次查詢；多跳題檢索 +21 點、答對 +15 點（GPT-3）。C3（先查電動機電流、算完才知道要查導線表哪一列）就是這種題。
- **Dense RAG vs GraphRAG，單次 vs agentic**（arXiv 2604.09666）：改成 agentic 搜尋後，dense RAG 在多跳題大幅進步，原因是拆查詢加多輪檢索。
- **預算受控的多跳檢索 agent**（MultiHop-RAG，2025-12 期刊論文）：單次檢索常漏掉後面幾跳；但要當成本對準確率的取捨看。
- **17、26**：decomp 撈全 .60 → .77（@4000），但子查詢是答題前一次拆完，看不到第一次查回來的東西。
- **搜了沒找到**：法規附表、兩張表接力查的題上，「模型自己查」對「固定流程」的受控比較。網路上「agentic RAG 34% → 78%」之類的數字多半出自廠商部落格，查不到原始論文，不採用。

**計畫**：跑前寫好，Mike 2026-11-04 核准。

**題庫與尺**：跟 26 一樣。16 的 160 題、五條鏈（C1 單查、C2 查＋修正、C3 馬達分路、C4 幹線需量、C5 設備接地）；5 題 defect 不計分，有答案 127 題、該棄答 28 題。尺照 26（數字 ≤ 1%；選型題小一級是 critical；棄答題 `found:false` 才對；單位嚴格；被停或解析不了算錯）。

**工具**（`search.py`）：
- 17 的 cards 檢索，換成模型寫的查詢：一條一塊的條文＋每張表一張卡片，bge-m3 排前 50，卡片換成整張表，打包 3,000 字（放不下的跳過）。
- 沒有狀態：同一個查詢回同一份。
- 測試鎖住：拿題目原文去查，160 題回傳都跟 17 存的 cards 依據逐字相同、命中相同。bge-m3 digest `790764642607`，跟 17 相同。

**提示**（`prompts.py`）：17 的規則段逐字，只把依據那行換成「本題不附原文。請用 search 工具查《用戶用電設備裝置規則》的條文與附表，每次回傳約 3,000 字，最多查 5 次；查到足夠的依據再回答。上面規則裡的「依據」，指 search 查回來的文字。」

**迴圈**（`claude.py`）：
- 手動 tool use 迴圈，每輪把整段對話送回（模型那一輪原樣，含思考區塊）。
- `tool_choice` 用 auto；工具 `strict: true`；最後一輪用 structured outputs 回 26 的 schema。
- 第 6 次起的查詢不查，回錯誤「已達查詢上限」；一題超過 8 輪算被停。
- 開自動提示快取；每輪都記帳，一般輸入、快取寫入（1.25×）、快取讀取（Opus 0.05×、Haiku 0.1×）分開算。
- effort medium、不設 temperature，跟 26 一樣。

**條件與次數**：
- `agent`：Haiku 每題兩次（第二次 `agent-2` 當雜訊底線），Opus 一次。共 480 題次。
- 基線讀 26 的列：cards、decomp@4000、oracle（同模型、同一天），用同一把尺重算；測試鎖住跟 26 算出來的一樣。
- 記每題的查詢、輪數、所有搜尋回傳的標籤聯集（撈全用這個算）、token。
- 累計超過 US$25 就停，停下來問 Mike。失敗的題整題重問；被停的不重問。score 碰到失敗列、過期列（簽章不同）或缺格就拒絕算分。

**花費估計**：計畫時估約 US$17（Opus 約 US$0.10／題）、約 2.5 小時；試跑後改估約 US$6、約 1 小時（見下；實際 US$6.47、50 分鐘）。

**主檢定**（跑前宣告；答對嚴格，有答案的 127 題；按題與按 cluster 兩種 bootstrap 的 95% 區間都不含 0 才算分得出）。每個模型各兩個：
1. agent − cards：同一個索引、同一種打包，只差「模型自己寫查詢、能查多次」。
2. agent − decomp@4000：自己查有沒有贏過最好的固定流程。

**描述、不下判定**：撈全率；按鏈；撈全／沒撈全時的答對；每題查幾次、沒查就答、引句在不在查到的文字裡；花費；該棄答的題、選小一級；Haiku 兩次同答。

**預期**（寫在計畫裡，核准時就定了）：
- **撈全率**：Opus .85–.95、Haiku .75–.90（decomp@4000 .77）。C3、C2 進步最多。
- **答對**：
  - Opus agent .80–.90；agent − cards +.20～+.30，分得出；agent − decomp@4000 +.05～+.15，可能分不出。
  - Haiku agent .70–.85；agent − cards 分得出；agent − decomp@4000 分不出。
- **查詢次數**：Opus 平均 2–3 次，Haiku 1–2 次；Opus 沒查就答 ≤ 5 題。

- **每題花費**：Opus 約 cards 的 5 倍（cards US$0.018／題）。

**跑前審查**（另一個 agent，用假的 API client 與 mock transport 離線查過，沒打 API）：沒有會讓數字錯或白花錢的問題。確認了：
- `search.py` 就是 17 的 cards 檢索；複製來的 `chunkers`、`evidence`、`retrievers`、`rules`、語料、題庫跟 17 逐位元相同。
- 跟 26 比是同一把尺：defect 一樣跳過、撈全一樣算、可答題配對 127 題。
- 送出的請求：上層 `cache_control` 與 `output_config` 收得下；模型那一輪原樣送回時，思考區塊（含簽章）、文字、tool_use 都不變。
- 每輪先記帳再可能出錯；價錢對得上；失敗、被蓋掉的列都算進上限。

照建議改的小地方：
- 被停的題也記下被擋的查詢次數、request id、模型名。
- 第 8 輪還在查就直接停，不再跑那輪的搜尋（不然結果模型看不到，卻算進撈全）。
- 簽章加上搜尋的預算、深度、bge-m3 版本、effort、max_tokens。
- 連續 5 題失敗就停（例如每題都回 400），不要白付 480 題的第一輪。

沒改、要記得的：
- 程式中途當掉或按 Ctrl-C，正在問的那題已付的輪數不會寫進帳裡。
- agent 的撈全是最多 5 次 × 3,000 字的聯集，26 是 3,000 或 4,000 字，預算不對等。
- 引句檢查是去空白後的逐字比對，模型改寫格式就算不在，只能當下限。
- Opus 只跑一次，主檢定沒有它自己的雜訊底線（計畫就這樣定）。

**試跑**（2026-11-04 15:30，寫到暫存資料夾，不算進結果；**預期在試跑之前就寫好了**）：

## 4. 結論

讓雲端模型自己查（最多 5 次、平均 1.6–1.9 次），正解列撈全率從固定流程最好的 .77 推到 Opus 1.0、Haiku .93，答對 Opus 127/127、Haiku .98／.96，比最好的固定流程 +.24（分得出），每題只貴約 2 倍（Opus US$0.038）。

## 5. 沒做到的、下次想試的

- **這批題對雲端模型自己查已經到頂**，分不出更好的做法了。要再往下比，題目得更難：更大的語料（好幾部規範、上千頁，而不是一部規則 1,014 條＋109 張表）、要三張表以上接力的題、或拿真的規格書和圖面出題。
- **語料小是這次贏這麼多的條件之一。** 模型知道表名怎麼說（「PVC管 導線安培容量」），一查就中。語料一大、同名的表一多，查詢可能沒這麼準；工具回整張表也是關鍵（26 的 oracle 只給一列反而輸）。沒測只回幾列的工具。
- **Opus 只跑一次**，它的 127/127 沒有自己的雜訊底線（計畫就這樣定）。Haiku 兩次差 .02。
- **Haiku 自己查時多了一種錯：表格空白格不棄答**，拿鄰欄推一個值（兩次各 2 題）。固定檢索時沒有。要上線就要程式擋：quote 那一格是空白就改判棄答；選出的線徑載流量要程式驗算（Haiku 選小一級各 1 次）。
- **引句檢查要比數字，不要比字串**：模型會改寫格式，逐字比對只抓到一成。
- 沒試 Sonnet 5.5、沒試 effort low 能不能更省；沒試把查詢次數上限降到 2–3 次（Opus 沒有一題用到 5 次）。
