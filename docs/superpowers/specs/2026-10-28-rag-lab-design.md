# rag-lab 專案說明（設計文件）

日期：2026-10-28。談定人：Mike。整理：Claude。
狀態：2026-10-28 Mike 核准（「先直接做，再看怎麼調」）。下面「審稿後補定」五點是 Claude 的決定，Mike 可改。

## 這是什麼

一個**長期的個人實驗室**，練「把資料餵給語言模型、讓模型吐出可靠東西」這條線上的技術：
文件切分與檢索（RAG）、固定格式輸出、掃描文件 OCR，以及之後看到的新方法
（rerank、GraphRAG、長文脈 vs 檢索的取捨……）。

**為什麼做**：先前做 securag 時切分只用了 LangChain 預設的 1000/200，沒比過、沒量過。
實務上「從雜亂的原始資料與規則算出配電回路規格」這類題目要接 LLM、做 RAG、寫提示詞、
可能要 OCR，還要避免幻覺與欄位矛盾。這裡把這類憑經驗選的參數一個一個量出來，給之後的
RAG 專案一個有數字的依據。Mike 自認這一塊知識缺，手上有機器與時間，先練。**沒有期限。**

## 產出是什麼（Mike 的決定）

**實驗紀錄為主，程式碼順便。** 每個實驗的價值在一頁紀錄：試了什麼、數字多少、所以學到什麼。
程式碼只是產生數字的工具，不需要寫成產品。類比：`~/Projects/infer-bench` 的
「建立憑證，不是做產品」。

成功的樣子：Mike 能用一句話講出一個有數字支撐的結論，例如
「照章節切比固定長度切命中率高 0.2，因為法規條文邊界重要」。

## 收什麼、不收什麼（Mike 的決定）

**收**：資料進→模型出這條線上的任何技術。
- 文件切分與檢索（第一個實驗）
- 固定格式輸出：讓本機模型只能吐 JSON schema 規定的欄位，量格式錯誤率（第二）
- 掃描版圖面／PDF 的 OCR：能抽出多少文字（第三）
- 之後看到的新技術，一題一個資料夾插隊

**不收**：DXF 產圖與標籤排版。那是幾何問題，跟 LLM 幾乎無關，混進來會讓這裡堆一堆
ezdxf 程式碼。要練時另開小專案。

**反目標**（做到了也算失敗）：
- 什麼都碰一點、沒有一個實驗有結論
- 數字只有平均沒有區間，分不出是真差異還是雜訊
- 把它做成有前端有 API 的產品（securag 已經是那個了）

## 結構（Mike 的決定：B）

**每個實驗一個資料夾，自己帶自己的程式、題庫、結果、紀錄；重複就重複。**
理由：第三個實驗改了共用程式，第一個實驗的數字就重跑不出來。數字永遠要能重跑。

```
rag-lab/
  CLAUDE.md          60 行內，只寫跟家裡層的差異
  HANDOFF.md         只寫「現在哪個實驗在跑、到第幾節」
  common/            很小。只放真的不會變的：連 ollama、讀 PDF 文字。改它要有理由
  experiments/
    01-chunking/     程式、題庫、結果、README.md（一頁紀錄）
    02-json-schema/
    03-ocr/
    ...
  data/              大檔（掃描圖面等，>10 MB），不進 git
  docs/
    superpowers/specs/   本文件與之後的設計
    summary.md           跨實驗總結，想比較時才寫
```

編號只表示先後，不表示重要性。資料夾名用英文。

## 一個實驗何時算完（Mike 的決定）

資料夾裡的 `README.md` 五節寫滿：

1. 想回答的問題（一句話）
2. 怎麼做：資料、方法、模型名稱與版本、日期、哪台機器
3. 數字：附信賴區間（bootstrap），不只一個平均
4. 結論：一句話，能直接對外講的那種
5. 沒做到的、下次想試的

數字跑出來但第 4 節寫不出一句話，就表示還沒完或題目問錯。老實寫第 5 節。

## 資料與 git（Mike 的決定）

- 公開法規 PDF、手工標的題庫、結果 CSV：**進 git**（單檔 ≤10 MB）。
  理由：題庫是手工，丟了要重做；兩台機器 pull 下來就能重跑。這是對家裡層
  「資料集不走 git」規矩的**明示例外**。
- 大檔（掃描圖面、模型權重）：`data/`，不進 git，各機各一份。模型走 ollama。
- GitHub repo **公開**。內容是公開法規與自己出的考卷，沒有客戶資料。紀錄就是作品集。

## 模型（Mike 的決定；核准後才拉）

- 向量模型：`bge-m3`（約 1.2 GB），中文強
- 聊天模型：`qwen3:8b`（約 5 GB），中文好；兩個一起放得進 mini 24 GB
- 現有的 `gpt-oss:20b` 留著，可當第二個聊天模型來比
- 一律走 host 的 ollama `127.0.0.1:11434`，不開 container（家裡層規矩）

## 節奏（Mike 的決定）

- **一次只開一個實驗**，做完一個再開下一個。理由：mini 一次只載一個大模型，兩個實驗搶模型互相拖慢；HANDOFF 也說不清。
- 沒有期限。長期實驗室。
- 順序：01 切分與檢索 → 02 JSON 固定輸出 → 03 OCR；新技術看到再插隊。

## 工作方式（沿用家裡層規矩）

- 每個實驗開工前，先用 plan mode 提計畫，計畫要寫「別人怎麼解的」（查過的前人做法，
  查不到也寫搜了什麼）。核准再寫程式。
- 評測照 Mike 定過的五條規矩：雜訊底線、bootstrap 信賴區間、盲測基線、記版本、漂移探針。
- 文件中文、程式英文。回報白話、一次一個重點（Mike 常在手機上看）。
- 不開 port；PORTS.md 登「不開 port」那一表。
- 骨架用 `new-project` skill 產生，不手寫。

## 第一個實驗（01-chunking）的邊界，Claude 的建議，核准後再寫正式計畫

一份法規 PDF、一張約 30 題的考卷、三種切法，回答「哪種切法在這份文件上找得最準、為什麼」。

- 題庫：Claude 出題、Claude 標答案到「條號」（不到段落，才不會被切法綁死），Mike 抽查 5 題看問法像不像人。
- 切法至少三種：固定長度（securag 現用的 1000/200 當基線）、照章節條文、照表格。
- 命中：找回的前 k 段裡有沒有包含正確條號。k 與其他細節在正式計畫裡定。
- 用 LLM 自動生題庫留到之後，那本身是一個實驗（生成題庫的偏差）。

## 審稿後補定（2026-10-28，Claude 的決定，Mike 可改）

審稿 subagent 問的五題，Mike 說「先直接做」，Claude 定如下：

1. **評測五條規矩套到檢索**：檢索是確定性的，三條用等價物，README 第 3 節要寫明用了哪個等價物，不准寫 N/A。
   雜訊底線 → 隨機抽 k 段的命中率；盲測基線 → BM25 關鍵字檢索；漂移探針 → 記 ollama 模型 digest，重跑驗同值，不做 cron。

3. **題數**：先 30 題附 bootstrap 區間；分不出來就寫「差距小於 X，30 題分不出」，第二輪加到 60。
4. **命中怎麼算**：兩個都報，hit@k 與「固定字數預算內有沒有命中」；對外那句結論用後者，段切得大不算贏。
   題型分層出題、分層報數字，各層題數照法規內表格與條文的實際比例。
5. **向量模型**：統一 bge-m3。securag 的 all-MiniLM-L6-v2 是英文模型，不沿用；只沿用它的 1000/200 切分參數當基線。
