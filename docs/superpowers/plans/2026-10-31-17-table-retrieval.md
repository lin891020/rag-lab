# 實驗 17：怎麼把對的表格列找回來——16 的檢索瓶頸，換「先找表、整張給」與「分步查」各救回多少 — 計畫（核准版存檔）

日期 2026-10-31，mini。16 的程式、題庫、乾淨表照用（讀 16 的 `questions.jsonl`、`corpus/tables_clean.json`；程式照規矩複製進 17，不共用）。語料仍是公開的《用戶用電設備裝置規則》。

## Context

16 的結論：查表接計算，答對與否幾乎全看正解列有沒有進依據（oracle .88／.68 vs 檢索 .28／.22；正解列全進只有 .41）。今天用 16 的嵌入快取（沒打模型）量了排名：

| 鏈 | 正解列在 dense 前 5 | 前 50 |
|---|---|---|
| C1 單查 | .04 | .27 |
| C2 查＋修正 | .06 | .21 |
| C3 馬達 | .00 | .13 |
| C4 需量 | .85 | 1.0 |
| C5 接地 | .81 | 1.0 |

C1–C3 的正解列**連前 50 都進不去**：前幾名被 87 張原始表的逐列塊佔滿（每塊都重複一大段表頭，例：表七二八～一 五塊）；而且 C3 要的導線列取決於算出來的電流，題目裡根本沒有那個數，一次查詢不可能撈到。→ **在前 50 上重排（12 的 bge）救不了 C1–C3**，要換找法。

## 1. 使用者要的是什麼（原話）

- 我講完 16：「如果之後要做下去，第一個該修的是檢索，例如每一步分開查」，Mike：「我們不先做嗎　還是沒有必要？」→ 我建議先做「改怎麼找」、「把規則寫成程式」等 11/2 之後 → Mike：「好」。
- 一直以來的規矩：實驗完整跑、機器不空、不反覆上下模型；計畫要有「別人怎麼解的」；五條評測規矩；README 五節。
- 成功的樣子：一張表，幾種找法 × 兩模型的「正解列全進依據」與答對率、選小率；一句話回答「哪種找法救回多少、離 oracle 還差多少、差在哪一鏈」。

## 2. 可能會錯在哪（每條有防呆）

| 會錯的地方 | 為什麼 | 怎麼防 |
|---|---|---|
| **贏是因為給的字比較多，不是找法比較好** | 整張表 ~930–1,180 字，C3 要兩張表加規則，1,500 字塞不下，預算得拉到 3,000 | 加一格 **struct@3000**（16 的找法、同預算）當對照；主檢定比的是「新找法 − struct@3000」，預算效果另列「struct@3000 − struct@1500」 |
| **依據變長，模型讀不好** | 長依據可能稀釋（04 整張表餵進去是好的 .79／.91，但那時只有一張表） | struct@3000 同樣長，對照得出；另報「正解列全進時的答對率」看讀的損失 |
| **在題庫上調找法 = 偷看考卷** | 卡片格式、k 值是看過這 160 題的失敗才定的 | 卡片格式寫死成通用的（表號＋表名＋欄名＋第一欄的鍵），不針對鏈；檢索軌所有試過的設定全列在 README（不只報最好的）；閱讀軌只跑事先選定的格，不回頭改 |
| **整張表的「命中」怎麼算** | 16 用 (表號, 列鍵) 標籤；整張表進來時，被預算截掉的列不能算命中 | 整張表放得下才放；第一張放不下就截，只把真的留在依據裡的列算命中（照 16 `budget_evidence` 的「第一塊一定讀」） |
| **分步查的子查詢由模型寫，等於多了一次模型呼叫、還可能把答案寫進查詢** | 拆題是 LLM 做的 | 子查詢**一律由 qwen3:8b 寫**（兩個閱讀模型共用同一份，快取成 `subqueries.jsonl`，README 寫明）；只准寫「要查什麼」不准寫答案（提示寫死、測試檢查子查詢不含題目裡沒有的數字…只記數，不擋）；子查詢的品質另報（有幾題拆出了兩張表） |
| **C3 的第二張表要靠算出來的數才查得到** | 分步查若只拆「查電動機電流表」「查導線安培容量表」，第二步不需要數字就能找表；整張表給，模型自己反查 | 這正是「先找表、整張給」的設計理由；README 寫明這裡做的是「拆成要哪幾張表」，不是 IRCoT 那種邊算邊查（放第 5 節） |
| **87 張原始表的卡片太亂** | 原始表頭是 pdf 文字層、有錯位 | 原始表的卡片用 01 `table_row_chunks` 的表頭行；它們是干擾項，亂是真實的；乾淨表 22 張整張用 markdown（16 的 `TABLES`），原始表整張用原文（截到預算） |
| **重排器搶記憶體、踢掉聊天模型** | 12 的 bge-reranker 走 torch／MPS | 重排只在檢索軌、閱讀軌開跑**之前**做完並快取；閱讀軌不載 torch |
| **題數太少分不出** | 130 題有答案、不一致率若 .3，半寬約 ±.08 | 預期的差距（檢索全進率 +.3 以上、答對 +.15 以上）遠大於半寬；cluster bootstrap 照 16（以鏈分層、按 (表, 列) 抽） |
| **跟 16 的數字對不上** | 16 跑完已一天、模型可能更新 | struct@1500 與 oracle 直接沿用 16 的 raw，**另重打每格 10 題當漂移探針**；digest 不同就整格重跑 |

## 3. 別人怎麼解的（查過的）

- **TableRAG（Google, NeurIPS 2024）**：大表不整張塞，先做 schema 檢索（欄名＋型別＋範例值）再做 cell 檢索；→ 這裡的「表卡片」就是 schema 檢索那一層；我們的表小（≤1,200 字），找到表之後整張給，不用再做 cell 檢索。
- **TableRAG（arXiv 2506.10380，異質文件）／ST-Raptor（2508.18190）／TabDSR（2511.02219）**：先把多跳題拆成子查詢、逐步檢索與計算；TTQA-RS（2406.14732）說模型一步做多層推理會掉分 → 「分步查」那一格。我們只做「拆成要哪幾張表」，不做邊算邊查（邊算邊查等於規則寫成程式那一步，11/2 後）。
- **列 vs 整張表**：Towards Data Science〈Retrieve one row, not the whole table〉主張查單一值用列、但「同一張表命中很多列時就改給整張」；LangChain〈Benchmarking RAG on tables〉說表格塊被本文塊擠掉，要上調表格塊權重。→ 都沒有受控的頭對頭比較，17 補這個（在我們的題上）。
- **本機**：12（bge-reranker-v2-m3 在 full 格 hit@1 .76 → .93，但前提是正解在前 50）；04（整張乾淨表餵進去 .79／.91）；07（dense＋BM25 RRF 沒幫助——在法規條文上）；16 的全套程式（`Evidence`、`budget_evidence`、`score`、`attribute`、cluster bootstrap）。
- **搜了沒找到**：針對「法規附表、要兩張表接力查」的檢索比較。

## 4. 設計

**一個問題**：把找法從「一列一塊、dense 前幾名」換成「先找表、整張給」或「先拆成要哪幾張表、分別找」，正解列全進依據的比例與答對率各回到多少、離 oracle 還差多少。

### 4.1 檢索軌（不用聊天模型；嵌入走快取、新卡片要算一次 bge-m3；重排用 torch）

| 格 | 索引 | 怎麼組依據 | 預算 |
|---|---|---|---|
| struct@1500 | 16 的一條一塊＋一列一塊 | dense 前幾名塞滿 | 1,500（16 原樣，對帳用：全進率須 = .41） |
| struct@3000 | 同上 | 同上 | 3,000（預算對照） |
| cards | 每張表一張卡片（表號＋表名＋欄名＋第一欄的鍵）＋一條一塊 | dense 排卡片與條文；表卡片命中 → 換成整張表（乾淨表 markdown、原始表原文）；依序塞到預算 | 3,000 |
| cards+rr | 同上 | dense 前 30 → bge-reranker-v2-m3（12 的 `CrossEncoderReranker`）重排 | 3,000 |
| decomp | 同 cards | qwen3:8b 先把題目拆成 1–3 個子查詢（「要查哪條規定、哪張表」）；每個子查詢各取 cards 排名，輪流塞到預算 | 3,000 |

指標（130 題有答案；按鏈、按題、cluster 三種）：正解列全進、正解表全進、正解條文進、依據字數。另列 BM25 RRF 一格只看檢索（07 的方法，便宜，不進閱讀軌）。

**閱讀軌要跑哪幾格，事先定**：struct@3000、cards、decomp 一定跑；cards+rr 只在檢索軌比 cards 的全進率高 ≥ .05 時才進閱讀軌（不然只報檢索數字）。

### 4.2 閱讀軌

- 模型：qwen3:8b、gpt-oss:20b，設定同 16（temperature 0、seed 0、num_ctx 8192——3,000 字依據約 2,500 token 放得下）。
- 提示與輸出：16 的 L1（`{found, quote, expression, value, unit}`，模型自己填 value）；不加計算工具（16 量過沒差，少一個變因）。
- 新跑：3–4 格 × 2 模型 × 160 題 = 960–1,280 次（約 9–10 秒一次 ≈ 2.5–3.5 小時）＋子查詢 160 次。
- 沿用 16：struct@1500（L1-struct）、oracle（L1-oracle）的 raw；每格重打 10 題當漂移探針。
- 尺、歸因、報表：16 的 `score.py`、`attribute.py`（歸因順序改成先看依據有沒有正解，再看棄答——16 第 5 節記的問題）、`report.py`。

**主檢定**（事先宣告，每模型 3 個，答對嚴格、130 題）：
1. cards − struct@3000（同預算，只換找法）
2. decomp − cards（加不加分步）
3. struct@3000 − struct@1500（預算本身）

**五條規矩**：雜訊底線＝16 的 L0（.01／.00）；盲測基線 struct@3000；bootstrap 95% 配對差距＋cluster；版本表；漂移探針（新格每格 2 題、沿用格每格 10 題）。

**預期**（事先宣告）：正解列全進 struct@3000 ≈ .5、cards ≈ .75、decomp ≈ .85（C3 主要靠它）；答對 cards − struct@3000 ≥ +.15（兩模型都分得出）；decomp − cards +.05～+.10（可能分不出）；struct@3000 − struct@1500 +.05 以內；最好的格仍比 oracle 低 .10 以上（依據變長、規則讀錯照舊）。

## 6. 順序

1. 複製 16／12 的程式；`cards.py`＋測試；`run_retrieval.py` 先跑 struct@1500 對帳（= .41 才往下）。
2. 檢索軌全跑（嵌入快取＋新卡片嵌入＋重排；不碰聊天模型以外的東西）；決定 cards+rr 進不進閱讀軌（照 4.1 的門檻，不看閱讀結果）。
3. `decompose.py`＋測試；跑前**獨立審查**（另一個 agent 審依據組法、命中判定、沿用 16 raw 的對帳）；全套測試 exit 0（deselect 兩檔）。
4. `chain17.sh`：子查詢 160 次 → 閱讀軌 → score → attribute → report；背景等候器。
5. 跑完：README 3–5、根 README 一列、playbook §7 補一條、HANDOFF、memory、commit、push；回報 Mike 一句話。
