# 實驗 19：通用查表工具——查表交給程式，錯誤總數有沒有變少 — 計畫

日期 2026-11-01，mini。18 的程式、題庫、語料照用（複製進 19，不共用）。語料仍是公開的《用戶用電設備裝置規則》。

## Context

16–18 一路指向「小模型輸在查表」：給正解列 .88／.68，靠檢索 .28／.22（16）；撈對了 qwen3 還是讀錯（17 讀錯欄；18 改每格帶欄名後讀錯欄 8 → 3，但讀錯列 7 → 10，答對 −.02）。這次把「讀表」整段交給程式：模型只說要查哪張表、哪一列、哪一欄，程式回那一格，模型再用查到的數字作答。要量的是錯誤從「查錯格」搬到「讀錯條件」之後，總數有沒有變少。

## 1. 使用者要的是什麼（原話）

- 我：「先做小一點、通用一點的版本，不要一開始就把每條規則都寫成程式」「一個通用的查表工具就夠：給『哪張表、哪一列、哪一欄』，回傳那一格；『以下』範圍表也用同一個規則處理」「先跑 C1、C4、C5」「量得到錯誤從查錯格搬到讀錯條件之後，總數有沒有變少」→ Mike：「好」，後來「為什麼不現在跑 還是要等？你判斷如何」→ 我說 11/2 沒有技術理由，現在先提計畫。
- 成功的樣子：一句話回答「查表交給程式，qwen3／gpt-oss 在 C1、C4、C5 答對各變多少，剩下的錯在哪一步（選錯表、選錯列、選錯欄、算錯規則）」。

## 2. 可能會錯在哪（每條有防呆）

| 會錯的地方 | 為什麼 | 怎麼防 |
|---|---|---|
| **工具＝答案產生器** | `rules.py` 的 `ampacity()`、`ground_conductor()` 就是出 gold 的程式，拿來當工具等於直接給答案 | 工具只讀 `tables_clean.json` 的格子，不呼叫任何 `rules.py` 的規則函式；選表（60／75／90℃、金屬管／PVC）、選列、選欄、分段累進全留給模型。測試：工具模組不 import 規則函式 |
| **範圍比法跟 gold 共用一份程式** | 「以下／超過／至」要比大小；若用 `rules._in_range`，它有錯時工具和 gold 一起錯，看不出來 | 照 Mike 談定的「同一套比法」重用 `_in_range`，但先對 22 張表所有範圍列鍵寫手算期望的測試（含邊界 800 vs 801、「3,001至120,000」）；README 寫明共用 |
| **比的不是只有讀表** | 查表格不用檢索（目錄有 22 張表），cards 有檢索 | C1／C4／C5 在 cards 的正解列全進率 .96／1.0／1.0，檢索幾乎沒漏，差距主要是讀表；README 寫明，並另比 oracle（直接給正解列，17 的格） |
| **目錄太長、模型挑不到列** | 22 張表的表名＋短欄名＋列鍵合計約 3,158 字 | 跟 cards 的 3,000 字同級；列鍵照 `row_key`，欄名照 18 的 `short_names`；最長提示先各送一次看 `prompt_eval_count` |
| **列名對不上就失敗** | 模型寫「2.0mm 單線」而列鍵是「單線 2.0」 | 對列：去空白、逗號、單位後完全相同；或「前綴＋一個數字」落在該前綴的範圍列。都不中就回「查無此列」，不猜；每次查詢結果與失敗原因都記下 |
| **只查一輪** | 模型看到「查無此列」不能再查 | 這三條鏈都不需要先算再查（C3 才要），一輪夠；README 寫明；「查無」次數照報 |
| **C4 的棄答靠條文** | 「住宅計算負載 < 100 A 不適用」寫在第 60 條，不在表 | 查表結果附上表的「註」，不附條文；這幾題（6 題，屬於該棄答題）不進主檢定，另外描述 |
| **gpt-oss 重跑會飄 .03–.04** | 17、18 量到 | gpt-oss 的查表格整格跑兩次；主檢定用第一次，第二次報同答與差距；差距要 > .05 才講 |
| **兩步提示跟 17 的提示不同** | 第二步多了「查表結果」這種依據 | 第二步用 17 的 `user_prompt` 逐字，只換依據內容與標籤（「查表結果」），JSON 欄位與評分不變 |

## 3. 別人怎麼解的（查過的）

- **Text-to-SQL／TableRAG（Chen et al., NeurIPS 2024, arXiv 2410.04739）**：模型先寫「要哪些欄、哪些格」的查詢，程式去表裡撈，再交給模型；schema 檢索 +9.4%、cell 檢索 +11.5%（GPT-3.5、Gemini 1.0）。→ 我們的工具就是它的「cell 檢索」縮成一個精確查詢。
- **NeedleInATable（arXiv 2504.06560）**：模型「照內容找格」比「照位置找格」好很多，中間位置最差。→ 跟 17／18 的讀錯欄、讀錯列一致；預期交給程式後這兩種錯消失。
- **TabIS（資訊檢索表格評測，12 個模型含小模型）**：模型對表格結構理解差、容易被看起來相關的表騙。→ 預期「選錯表」會變成主要錯誤（60／75／90℃ 三張）。
- **SemEval-2025 Task 8 TableWise**：小模型（Mistral-7B、Llama-3.2-3B）呼叫工具查表能改善，但大模型會陷在工具迴圈。→ 我們只查一輪，避開迴圈。
- **本機 16**：計算工具 +.00～+.04（算術本來沒錯）；PAL／PoT 類「程式算」救的是算術，不是查表。
- **搜了沒找到**：同一個小模型「整張表給它讀」vs「它下查詢、程式回格子」的受控比較。

## 4. 設計

**一個問題**：查表交給程式（模型只下「表、列、欄」），C1、C4、C5 答對率比 cards 多多少，剩下的錯在哪一步。

### 格

| 格 | 依據 | 閱讀軌 |
|---|---|---|
| cards | 18 的 cards（qwen3 沿用 17、gpt-oss 沿用 18 重跑），只取 C1／C4／C5 | 不重跑（探針各 2 題） |
| oracle | 17 的 oracle（直接給正解列），只取 C1／C4／C5 | 不重跑 |
| lookup | 第一步：題目＋表目錄 → `{"lookups":[{"table","row","column"}]}`（最多 6 筆，schema 限定）；程式查格；第二步：17 的 `user_prompt`，依據＝查到的格（`表｜列｜欄 = 值`、空白格寫「（空白）」、查無寫原因）＋用到的表的註 | 兩模型新跑；gpt-oss 跑兩次 |

模型與設定照 17／18（qwen3:8b think 關、gpt-oss:20b think low；temperature 0、seed 0、num_ctx 8192、num_predict 1024）。

**主檢定**（事先宣告，答對嚴格，C1＋C4＋C5 有答案的 78 題，配對 bootstrap 95%＋cluster，照 18）：lookup − cards，每模型 1 個。

**描述（不下判定）**：lookup − oracle；按鏈；第一步的命中（正解表／正解列有沒有被查到、欄有沒有對）；新歸因：選錯表／選錯列／選錯欄／查無／查對但答錯（規則或算術）；gpt-oss 兩次的同答與差距；該棄答 18 題。

**五條規矩**：雜訊底線＝gpt-oss 兩次；盲測基線 cards；bootstrap＋cluster；版本表（digest 須與 18 同）；漂移探針（沿用格各 2 題）。

**預期**（事先宣告）：qwen3 lookup − cards +.15～+.30，分得出，C5 最大（範圍比法交給程式）；gpt-oss +.00～+.10，可能分不出（它本來讀得懂）；兩模型 lookup 仍低於 oracle 不超過 .10；剩下的錯以「選錯表／欄」（溫度、條數讀錯）和 C4 分段累進為主。

**呼叫數**：96 題（C1／C4／C5 含棄答）× 2 步 × (qwen3 1 次＋gpt-oss 2 次) ＝ 576 次，第一步輸出短；估 1.5–2 小時。先 qwen3、再 gpt-oss。

## 6. 順序

1. 複製 18；先寫 `test_lookup`，看它失敗，再寫 `lookup.py`。
2. 不用模型的檢查：拿 gold 的（表、列）餵工具，C1／C4／C5 每題都查得到正解格（96/96，棄答題查到空白／「-」）；目錄長度、最長提示字數。

4. `chain19.sh` 背景跑。
5. 跑完：README 五節、18 README 第 5 節指到 19、根 README 一列、playbook §7 一條、HANDOFF、memory（如有新雜訊數字）、commit、push；回報 Mike。
