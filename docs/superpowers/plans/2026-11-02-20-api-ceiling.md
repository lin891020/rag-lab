# 實驗 20：強模型上限——「點錯格」只有小模型會犯嗎 — 計畫

日期 2026-11-02，mini。19 的程式、題庫、語料照用（複製進 20，不共用）。語料仍是公開的《用戶用電設備裝置規則》。模型改走 Claude API（Mike 11/2 同意；Max 方案每月送的 US$100 額度，11/24 到期）。

## Context

16–19 一路指向「小模型輸在知道要表上哪幾格」：19 把讀格子交給程式後，查到時答對 .86／1.0，但總分沒升，錯搬到「選哪幾列」（C4 分段只查一段、C5「以下」讀反）。還沒回答的是：這是 8B／20B 太小，還是這種題本身難？用最強的模型跑同一組題，量出上限。

## 1. 使用者要的是什麼（原話）

- 我：「用 API 的強模型測測看，看這是不是只有小模型才有的問題」「先量出最強的模型能做到多好，30B 之後再看要不要補」→ Mike：「還是api的可以嗎？」，key 放好後「好直接用」。
- 成功的樣子：一句話回答「最強的模型在 C1／C4／C5 整張表給它讀、用查表工具、直接給正解列，各答對多少；它也會點錯格嗎」。

## 2. 可能會錯在哪（每條有防呆）

| 會錯的地方 | 為什麼 | 怎麼防 |
|---|---|---|
| **不能設 temperature 0** | Claude API 新版拒收 temperature；同題重問答案可能不同 | 每格整格跑兩次，第二次當雜訊底線（同 gpt-oss 的作法）；差距要 > 兩次差才講 |
| **模型會偷偷改版** | API 的 model id 沒有日期快照 | 記 model id、回應裡的 `model`、日期、`anthropic` 套件版本；兩次跑在同一天內 |
| **thinking 關不掉** | Opus 5.5 的 thinking 一律開，靠 effort 控 | 兩模型都明寫 `effort: "medium"`（Opus 5.5 預設值），記下 output token；跟 gpt-oss（think low）不是同一種設定，README 寫明 |
| **JSON schema 有幾個限制不收** | 官方不支援 `maxItems` 等數值限制 | 第一步 schema 拿掉 `maxItems`，靠既有的 `parse_lookups` 只取前 6 筆（19 已有、已測）；照記超過 6 筆的次數 |
| **拒答／截斷** | `stop_reason` 可能是 refusal 或 max_tokens | 每筆記 `stop_reason`；非 end_turn 的算 error 列、不算答案，報次數 |
| **依據跟 19 不同** | cards／oracle 要用 19 存下來的依據重問，不是重新檢索 | 從 19 的 raw 取 `evidence_text`，用 17 的 `user_prompt` 逐字組提示；測試：組出的提示跟 19 那列存的長度一致 |
| **花太多錢** | 有 thinking，output token 估不準 | 先試跑 3 題、看 `usage` 推算全部花費；推算 > US$40 就停下來問 Mike |
| **審查找到的 19 小問題帶過來** | c4-16 多算一列、no_column 歸成選錯列、測試函式內 import | 20 的複本先修這三處（各加測試），19 本身要不要修另外等 Mike |

## 3. 別人怎麼解的（查過的）

- **TABVERSE（arXiv 2606.09578，2026）**：跨格式表格評測裡，前沿模型的查表錯多半是「對的欄、錯的列」或漏掉一個篩選條件；多項答案常漏項——跟 19 的「分段只查一段」「以下讀反」同型。→ 預期強模型也會犯，但少。
- **ReasonTabQA（arXiv 2601.07280）**：工業場景表格題，Claude Opus 4.5 只有 66、GPT-5.2 59——前沿模型在真實表格上也不到七成。
- **Attributed Table Graphs（arXiv 2601.08444）**：Claude Opus 4.7 在 WikiTQ 78.6、TabFact 91.2，作者說精確篩選與比較仍是弱點。
- **TableBench（AAAI 2025）／Table-R1（arXiv 2505.12415）**：大小模型差距存在，但專門訓練能縮小。
- **搜了沒找到**：同一組題「小模型 vs 前沿模型」在「整張表 vs 查表工具 vs 給正解列」三種給法下的受控比較；也沒找到專講「以下／分段累進」範圍表的錯誤率。

## 4. 設計

**一個問題**：最強的模型在 C1／C4／C5 的三種給法各答對多少，它也會點錯格嗎。

### 格（每格 96 題，每格跑兩次）

| 格 | 依據 | 來源 |
|---|---|---|
| cards | 整張表（17／18 的 cards） | 19 raw 存的 `evidence_text` |
| fix | 兩步查表（19 的 fix 版：無例子、括號寬鬆） | 19 的 `lookup.py`、`lookup_prompt(fix=True)` |
| oracle | 直接給正解列（17 的 oracle） | 19 raw 存的 `evidence_text` |

模型：`claude-opus-5-5`（主角，最強且官方預設）、`claude-haiku-5-5`（便宜，看大小中間那段；描述用）。兩個都 effort medium、`max_tokens` 16000、`output_config.format` 照 19 的兩個 schema。同步呼叫一次一題（沿用 19 的續跑邏輯），不用 batch——量小，省下的錢不值得多寫兩階段批次。

**主檢定**（事先宣告，答對嚴格，有答案的 78 題，配對 bootstrap 95%＋cluster，照 19）：
1. opus cards − gpt-oss cards（強模型整張表讀得比小模型好多少；gpt-oss 用 19 的 cards 列）
2. opus fix − opus cards（查表工具對強模型是幫還是害）

**描述（不下判定）**：opus oracle、與 oracle 的差；haiku 三格；按鏈；`step1_class`（沒查／選錯表／選錯列／選錯欄／都查到）跟 19 兩模型並排；兩次跑的同答與差距；選小一級；該棄答 18 題；token 與花費。

**預期**（事先宣告）：opus cards .85–.95、oracle ≥ .95；opus fix − cards −.05～+.05 分不出；opus 在 fix 的「選錯列」比 19 兩模型少一半以上，但 C4 分段漏段仍有幾題；haiku 介於 gpt-oss 與 opus 之間。

**五條規矩**：雜訊底線＝每格兩次；盲測基線＝gpt-oss cards；bootstrap＋cluster；版本表（model id、回應 model、SDK 版本、日期）；漂移探針＝兩次跑本身＋19 的小模型列照抄不重跑（探針沿用 19 的紀錄）。

**呼叫數與花費**：96 題 × 4 次呼叫（cards 1、oracle 1、fix 2）× 2 次 × 2 模型 ≈ 1,536 次。估 opus 每次跑約 US$10–15（輸入約 0.9M token、輸出約 0.4M），兩次 US$20–30；haiku 不到 US$1。合計約 US$30，額度 100。試跑 3 題後用實際 `usage` 重算再開跑。
